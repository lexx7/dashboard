# Feature Specification: ETL-пайплайн «Источник → Витрина товаров»

**Feature Branch**: `001-catalog-sync-pipeline`

**Created**: 2026-09-08

**Status**: Draft

**Input**: User description: "Розничная сеть хранит каталог товаров в операционной системе («источник»). Аналитикам и витринным сервисам нужна отдельная копия каталога («витрина»), которую можно нагружать тяжёлыми запросами, не нагружая операционную систему. Цель: пайплайн, который переносит изменения каталога из источника в витрину с гарантиями целостности, возможностью восстановления после сбоев и контролем расхождений."

## Clarifications

### Session 2026-09-08

- Q: Каким способом пайплайн будет получать изменения каталога из операционной
  системы-источника? → A: Периодический опрос базы данных источника по полю `updated_at`
  записей каталога.
- Q: Что представляет собой витрина? → A: Новая реляционная БД (PostgreSQL), создаваемая
  в рамках фичи; физически отдельная от источника.
- Q: Есть ли у каталога чувствительные данные и требования к авторизации читателей? →
  A: Несensitive внутренние данные: доступ ограничен сетевым периметром, авторизация
  читателей не требуется.

### Session 2026-09-08 (ре-синхронизация под plan.md)

План (plan.md) переопределил скоуп; ранее принятые решения скорректированы:

- Удаления/деактивация товаров выведены за рамки v1: источник append/update-only
  (ранее — мягкое удаление по флагу `active`).
- Добавлены требования: staging-аудит сырых записей и обработка битых записей без

- Реконсиляция — по количеству записей (count), а не построчная/по хэшам пачек
  (ранее — полная сверка пачками); поэлементная сверка отнесена в backlog.
- Мониторинг прогонов — через таблицу прогонов и структурные логи (FR-8).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Инкрементальный перенос изменений каталога (Priority: P1)

Аналитики и витринные сервисы читают каталог из витрины. Пайплайн периодически переносит
новые и изменённые товары из операционной системы в витрину, не нагружая её лишними
запросами; неизменённые записи не затрагиваются.

**Why this priority**: Ядро ценности — без переноса изменений витрина бесполезна.

**Independent Test**: Внести в источник новые и изменённые записи, запустить прогон,
проверить, что витрина отразила именно их, а повторный (пустой) запуск ничего не меняет.

**Acceptance Scenarios**:

1. **Given** в источнике появились новые товары, **When** выполняется прогон, **Then**
   они появляются в витрине с полным набором полей.
2. **Given** товар изменился в источнике, **When** выполняется прогон, **Then** витрина
   содержит новые значения полей.
3. **Given** со прошлого прогона изменений не было, **When** выполняется прогон,
   **Then** состояние витрины не меняется (0 загруженных записей).

---

### User Story 2 - Восстановление после сбоя (Priority: P2)

Прогон пайплайна прерван сбоем посередине. После перезапуска пайплайн продолжает с точки
последнего подтверждённого батча — без потерь и без дублей, без ручного вмешательства.

**Why this priority**: Гарантия восстановления — явное требование цели; без неё любой сбой
требует ручной перезаливки.

**Independent Test**: Прервать прогон между батчами, перезапустить и проверить сверкой:
0 потерь, 0 дублей.

**Acceptance Scenarios**:

1. **Given** прогон прерван между батчами, **When** пайплайн перезапущен, **Then**
   необработанные записи применяются, а уже применённые не дублируются.
2. **Given** часть батча была в незавершённой транзакции при сбое, **When** пайплайн
   перезапущен, **Then** этот батч применяется заново целиком без побочных эффектов.

---

### User Story 3 - Устойчивость к устаревшим версиям записей (Priority: P2)

При повторной или внепорядковой обработке запись со старой меткой изменения не должна
перезаписать более новое состояние в витрине.

**Why this priority**: Иначе гонки и повторные прогоны «откатывают» данные витрины —
тихая порча данных.

**Independent Test**: Прогнать батч, где для одного товара старая версия обрабатывается
после новой; проверить, что в витрине осталась новая версия.

**Acceptance Scenarios**:

1. **Given** в витрине товар с `updated_at = T2`, **When** приходит версия с
   `updated_at = T1 < T2`, **Then** витрина сохраняет версию T2.
2. **Given** одна и та же версия приходит повторно, **When** она применяется, **Then**
   состояние витрины не меняется.

---

### User Story 4 - Запуск по расписанию и вручную (Priority: P2)

Пайплайн работает автоматически по расписанию без участия человека; для тестов и
эксплуатации доступен ручной запуск прогона и сверки через REST.

**Why this priority**: Автономность — базовое эксплуатационное требование; ручной запуск
нужен для crash-тестов и проверок.

**Independent Test**: Дождаться автоматического прогона по расписанию и отдельно вызвать
ручной запуск; оба видны в журнале прогонов.

**Acceptance Scenarios**:

1. **Given** настроено расписание, **When** наступает время срабатывания, **Then**
   прогон стартует автоматически и фиксируется в журнале прогонов.
2. **Given** пайплайн простаивает, **When** вызван ручной запуск, **Then** прогон
   выполняется и возвращает идентификатор прогона.
3. **Given** прогон уже выполняется, **When** вызван ещё один запуск, **Then**
   конкурентный запуск отклоняется (один инстанс пайплайна).

---

### User Story 5 - Аудит сырых данных и контроль расхождений (Priority: P3)

Все прочитанные из источника записи сохраняются «как есть» в staging-слое для аудита;
битые записи не прерывают батч, а попадают в журнал ошибок. Отдельная джоба сверяет
количество записей в источнике и витрине и возвращает отчёт о расхождении.

**Why this priority**: Аудит и сверка повышают доверие и отладку, но пайплайн доставляет
ценность и без них.

**Independent Test**: Прогнать батч с битыми записями и проверить staging, журнал ошибок
и витрину; удалить записи из витрины, выполнить сверку и увидеть расхождение в отчёте.

**Acceptance Scenarios**:

1. **Given** выполнен прогон, **When** смотрим staging-слой, **Then** каждая прочитанная
   запись сохранена «как есть» с привязкой к прогону.
2. **Given** в батче 1000 записей, из них 5 битых, **When** прогон завершается, **Then**
   995 записей в витрине, 5 — в журнале ошибок с причиной, прогон успешен.
3. **Given** из витрины удалено 100 записей минуя пайплайн, **When** выполняется сверка,
   **Then** отчёт возвращает расхождение 100.

---

### Edge Cases

- Несколько записей с одинаковым `updated_at` — курсор разрешает совпадения
  детерминированно (tie-breaker по `sku`), пачка не теряется при прерывании.
- Запись изменена в долгой транзакции, закоммиченной после прохода курсора — окно
  отставания (читаем только `updated_at < now() - 30s`) не даёт её пропустить.
- Битая запись (отрицательная цена, пустое обязательное поле) — исключается в журнал
  ошибок, батч продолжается.
- Пустой запуск (нет изменений) — витрина и чекпоинт не меняются.
- Повторный запуск того же диапазона — дублей нет (upsert по PK).
- Конкурентный запуск прогона — отклоняется блокировкой по статусу активного прогона.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-1**: Пайплайн MUST переносить новые и изменённые товары из физически изолированной
  операционной БД-источника в отдельную БД-витрину; чтение источника — только по курсору
  `updated_at` с индексом, без тяжёлых запросов.
- **FR-2**: Пайплайн MUST вести чекпоинт `(updated_at, sku)`; обработка каждого батча
  (staging → загрузка в витрину → продвижение чекпоинта) MUST быть атомарной — одной
  транзакцией на стороне витрины.
- **FR-3**: Пайплайн MUST быть идемпотентным: повторная обработка одних и тех же записей
  не создаёт дублей (upsert по первичному ключу `sku`).
- **FR-4**: Версия записи с более старым `updated_at` MUST NOT перезаписывать более новую
  версию в витрине.
- **FR-5**: Пайплайн MUST сохранять сырые прочитанные записи в staging-слой (аудит)
  с привязкой к прогону, в рамках транзакции батча.
- **FR-6**: Битая запись MUST валидироваться до загрузки, исключаться из батча и
  фиксироваться в журнале ошибок с причиной; батч MUST NOT прерываться из-за битых
  записей.
- **FR-7**: Пайплайн MUST запускаться автоматически по расписанию и MUST поддерживать
  ручной запуск прогона и сверки через REST; конкурентные запуски MUST отклоняться.
- **FR-8**: Система MUST фиксировать каждый прогон (статус, время старта/финиша, счётчики
  прочитано/загружено/ошибок) и писать структурные JSON-логи ключевых событий.

### Key Entities

- **Товар (источник/витрина)**: `sku` (PK), название, цена, `updated_at`.
- **Staging-запись**: сырой снимок записи источника, привязанный к прогону (аудит).
- **Чекпоинт**: курсор `(updated_at, sku)` последнего подтверждённого батча.
- **Прогон (etl_run)**: статус (`RUNNING`/`SUCCESS`/`FAILED`), время, счётчики
  staged/loaded/failed.
- **Ошибка записи (etl_error)**: запись, не прошедшая валидацию, с причиной.
- **Отчёт о сверке**: количество записей источника и витрины, величина расхождения.

### Термины

- **Витрина** — БД `db-mart`; таблица каталога в ней — `products_mart`.
- **Курсор**, он же **чекпоинт** / **позиция синхронизации** — пара `(updated_at, sku)`
  последнего подтверждённого батча, хранится в `etl_checkpoint`.
- **Прогон** — один запуск пайплайна, фиксируется записью в `etl_run`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-1**: Полный прогон по каталогу в 1 млн записей завершается в пределах ночного окна
  (не более 4 часов); замер фиксируется производительным тестом.
- **SC-2**: Инкрементальный прогон переносит 100% новых/изменённых записей; пустой запуск
  вносит 0 изменений в витрину.
- **SC-3**: После прерывания между батчами и перезапуска — 0 потерянных и 0
  продублированных записей (проверяется сверкой).
- **SC-4**: Сверка обнаруживает 100% искусственно внесённых расхождений по количеству
  (100 удалённых из витрины записей → отчёт о расхождении 100).
- **SC-5**: В батче из 1000 записей с 5 битыми — 995 загружены в витрину, 5 попали в
  журнал ошибок, прогон завершён успешно.

## Assumptions

- Источник — реляционная БД с таблицей товаров, у каждой записи есть `sku` (PK) и
  `updated_at`, обновляемая при любом изменении; по `(updated_at, sku)` есть индекс.
- В v1 источник append/update-only: удаления и деактивации товаров отсутствуют.
- Первичная загрузка — тот же курсорный механизм с нулевым чекпоинтом (полный проход по
  источнику батчами).
- Режим — близкий к реальному времени (минуты), строгая синхронность не требуется.
- Реконсиляция — по количеству записей; поэлементная сверка (по хэшам строк) — backlog.
- Один инстанс пайплайна; конкурентные запуски исключены блокировкой.
- Данные несensitive; доступ к витрине и REST ограничен сетевым периметром.
- Объём каталога — до ~1 млн записей; пиковые массовые обновления — до сотен тысяч за раз.
